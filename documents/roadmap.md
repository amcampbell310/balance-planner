# Balance Planner — Roadmap

Status as of 2026-08-17: the v1 core loop is fully built and verified live end-to-end — Google OAuth login, onboarding, Claude-drafted weekly plans, approval with correct per-user timezone handling, check-in, and both the generic-tip and personalized-suggestion recommendation paths. See `prisma/schema.prisma` and `diagrams/*.mmd` for the current data model and flows.

This doc tracks what's next. Phases are roughly sequential; the backlog isn't.

## Phase 1 — Scheduler / Reminder Worker ✅ complete (2026-08-18)

Built as the full Redis-queue architecture from the original diagrams (BullMQ), not a simplified single-script version — a deliberate choice to match the diagrammed design now rather than defer it. Runs as one persistent process (`npm run worker`, `src/worker/index.ts`), matching the already-decided Railway hosting plan.

- Four BullMQ queues (`src/backend/queue.ts`), each with one repeatable "sweep" producer (`src/worker/scheduler.ts`) rather than a literal per-user cron entry per the diagrams — per-user/timezone-awareness lives in each job's own eligibility logic instead (using `User.timezone`/`weekStartDay`), which avoids maintaining N schedules that shift on every onboarding/timezone change. `checkin-reminder` sweeps every 15 min; `draft-pending`, `inactivity`, `trend-refresh` sweep daily.
- `src/backend/jobs/checkInReminder.ts` — creates `PENDING` `CheckIn`s and sends `CHECK_IN_REMINDER`. Scans a bounded 8-week lookback (not just "last week"), so it self-heals and catches up correctly if the worker was ever offline — consolidated into one email per user per sweep even if several weeks piled up at once, never a burst.
- `src/backend/jobs/draftPending.ts` — `DRAFT_PENDING`, once per `WeeklyPlan`, respecting the 7-day anti-spam throttle.
- `src/backend/jobs/inactivity.ts` — `RE_ENGAGEMENT` after 14 days inactive, 30-day resuppression, same 7-day throttle.
- `src/backend/jobs/trendRefresh.ts` — wires `analyzeTrends()` (previously unused) into the `PATTERN_INSIGHT` recommendation type, ~14-day refresh cadence, 16-week bounded history lookback.
- Email via Resend (`src/backend/email.ts`) — live and verified.
- Redis runs locally via Docker on port 6380 (6379 was already taken by an unrelated project's container on this machine).

**Verified live**, not just typechecked: the real running worker autonomously fired its first trend-refresh sweep and generated a genuine, accurate insight ("Game Night with Friends... consistently missed... across all four weeks") via a real Haiku 4.5 call. Every job's positive path and its "correctly does nothing" path were exercised by hand against seeded scenarios, including confirming the anti-spam throttle actually suppresses one job type when another just fired for the same user. A real test email was sent and confirmed received.

**Known gap, deliberately deferred**: no retry/dead-letter handling beyond BullMQ's defaults, and the `every`-based sweep intervals are a simplification of "per-user timezone-aware cron" (see above) — revisit if this ever needs tighter timing precision than "within 15 minutes of a boundary."

## Phase 2 — Prompt Tuning ✅ complete (2026-08-18 – 2026-08-23)

Built `scripts/eval-prompts.ts` (`npm run eval:prompts`) — 5 `generateWeeklyDraft` scenarios (normal case, empty priorities, single selected category, packed schedule, overlapping/inconsistent existing items), 3 `generateMissedItemSuggestion` scenarios (no history, clear pattern, unhelpful statusNote), and 4 `analyzeTrends` scenarios (clear negative pattern, clear positive pattern, no pattern/noise, insufficient data) — re-run after every prompt change instead of eyeballing one output at a time.

First pass (draft/suggestion prompts) found two real issues, both fixed and re-verified live in `src/backend/claude.ts`:
- **Bug**: with `selectedCategories: ["WORK"]`, the model proposed SOCIAL and GAMING items anyway — direct violation of the system prompt's existing "only use categories from the user's selected set" instruction. Prompt wording alone wasn't reliable enough, so added a **programmatic backstop**: `generateWeeklyDraft` now filters `items` down to `selectedCategories` before returning, regardless of what the prompt achieves.
- **Quality**: empty/vague priorities produced a maximalist, presumptuous 15-item week filling every day. Added explicit guidance to propose a light, modest week in that case instead — re-verified live, now produces ~5 well-chosen items.

`generateMissedItemSuggestion` held up well across all three scenarios with no changes needed.

**`analyzeTrends` eval pass (2026-08-23)** — the last open Phase 2 item, added once there was a reason to revisit it. Its system prompt had the exact same class of hard-constraint-in-prose problem as the category-filtering bug above: "if nothing recurs clearly, say so honestly rather than inventing a pattern" wasn't actually being followed. The "no clear pattern" scenario (a single missed SOCIAL item among otherwise unrelated data, no real repetition) still got reported as "SOCIAL category items are not being completed" — a fabricated pattern from one data point. Fixed by tightening the prompt to explicitly require the same outcome recurring across **at least two or three distinct weeks**, state plainly that "a single occurrence... is never a pattern," and give an example honest phrasing for the no-pattern case — re-verified live, now correctly returns `"no clear recurring pattern yet"` / `category: null` for both the noise and insufficient-data scenarios, with the two genuine-pattern scenarios unaffected. General lesson reconfirmed: a "hard constraint" stated only in a system prompt is a hypothesis, not a guarantee — eval it, don't assume it holds just because it reads clearly.

## Phase 4 — Live-usage-driven drafting refinements (2026-08-24)

Found through actually using the approved-week flow after several real weeks of data existed, not pre-planned — the same pattern as most of this project's real bugs.

- ✅ **Explicit priority requests outside selectedCategories no longer just silently drop** — `WeeklyDraftSchema` (`src/backend/claude.ts`) gained a structured `excludedRequests` field (description + category), and the system prompt now directs Claude to record explicit, specific requests there instead of vaguely mentioning them in the summary or dropping them without a trace. The hard category filter (the Phase 2 programmatic backstop) stays absolute — nothing slips through silently, this only makes the *exclusion* visible and actionable. `WeeklyPlanner.tsx` renders each excluded request as a callout with an "Add {category} & regenerate" button that updates the account's selected categories and immediately regenerates with the request as the adjustment text. Verified live via `scripts/eval-prompts.ts`'s existing "single selected category" scenario, which was already the perfect test case (asks for gaming + a date night with only WORK selected) — confirmed both requests land correctly in `excludedRequests` with zero false positives across every other scenario.
  - **Real backward-compatibility bug found and fixed in the same pass**: any `WeeklyPlan` still `PENDING` from before this schema change has a stored `draftJson` without the new field, so reading `draft.excludedRequests.length` on an old draft threw and crashed the whole page. Fixed by defaulting `excludedRequests` to `[]` wherever a stored draft is read, not just typing it as required and hoping every draft matches the current shape — a reminder that a Zod schema change doesn't retroactively update JSON already sitting in the database.
- ✅ **"Same as last week?" recurring-item autofill** — before a new week has a plan yet, `WeeklyPlanner.tsx` compares this week's items against last week's (fetched via the existing `getWeekData`/`addWeeks` helpers) using a title+category+day-of-week+local-time signature, and shows any unmatched previous-week items as a checked-by-default checklist ("these looked the same last week — copy them?"). Confirming posts each checked item through the existing `POST /api/plan-items` route, computing the new week's actual date via `dayOfWeekToDate`. Solves the real gap this surfaced from: recurring commitments (a fixed work schedule, in the case that prompted this) had no way to carry forward week to week short of manually re-adding them or hoping Claude's draft inferred them correctly.
- ✅ **Priority quick-add chips** — a row of dashed pills above the priorities box (date night, game night, gym session, time with friends, chores, keep it light, pack the week). Clicking appends the phrase to the text box with sensible punctuation rather than replacing it — a faster on-ramp into the same free-text flow Claude already handles well, not a new input format.
- ✅ **Draft review became a modal** — the summary/excluded-requests/approve/regenerate panel used to sit permanently inline, taking real vertical space for what's usually a couple sentences. Built this project's first modal (`Modal.tsx` — backdrop + centered panel, dismiss on Escape/backdrop-click/close button; everything before this was an anchored popover, the wrong pattern for a blocking review step with no natural anchor point) and moved that content into it. Auto-opens when a draft is created or on load if one's still pending; auto-closes on approve. When dismissed, a compact pill ("Week drafted — Review & approve") is the way back in — went through two rounds of live layout feedback, landing on its own centered row directly under the week picker (matching the centered title/picker above it) rather than inline in the left-aligned toggle/legend/add-item row, where it first went and looked out of place. Also fixed the Approve/Request-changes visual hierarchy in the same pass — "Request changes" moved into its own bordered card with a `.secondary`-styled button instead of a second full-width solid button competing with Approve.
- ✅ **Required name at signup + Personalization settings** (2026-08-25) — a credentials account created before this had `name: null` (the signup flow never collected one, unlike OAuth's profile-sourced name), so "Welcome back" had nothing to greet. First name is now required at credentials signup (`CredentialsForm.tsx`, `POST /api/auth/signup`) — `User.name` stays nullable at the DB level (no risky `NOT NULL` migration against existing rows), enforced as required at the application layer instead. New `PATCH /api/account` plus a `PersonalizationForm.tsx` section in Settings let it be set or changed later, including for the account that predates this requirement.
- ✅ **Forgot/reset password** (2026-08-25) — found via a real bug report: a wrong password just spun forever with no error. Root cause: Auth.js's client `signIn()` returns `ok: true`/200 even on a failed credentials login (failure is encoded as a redirect URL's `error` query param, not a 4xx) — `CredentialsForm.tsx` was checking `result.ok` instead of `result.error`, so a wrong password silently "succeeded," navigation was a no-op, and the loading state never reset. Fixed, then built the actually-requested forgot-password flow alongside it: new `PasswordResetToken` model (hashed token, 1-hour expiry, one-time use), `POST /api/auth/forgot-password` (always returns the same generic response regardless of whether the email is registered, same posture as signup's 409 check; an OAuth-only account gets a "you sign in with Google" email instead of a reset link), `POST /api/auth/reset-password`, and `/forgot-password` + `/reset-password` pages. A `sendEmail` failure (Resend's sandbox mode only delivers to its own verified address — a pre-existing constraint, not new) was initially propagating as a raw 500, which both broke UX and leaked account existence via the status code difference; fixed by catching send failures and always returning the generic response. Verified end-to-end by seeding a valid token directly in the database (Resend couldn't actually deliver to the test account) and running it through the real endpoint: token accepted, password updated, new password authenticates, reused token correctly rejected.
- ✅ **Data-export "Print / Save as PDF" button** (2026-08-25) — the export summary page claimed to be "ready to print or save as a PDF" but had no actual print action, just a JSON download link; a user naturally clicked that expecting a PDF. Added a real `PrintExportButton.tsx` (`window.print()`) so the existing-but-unused `@media print` styles actually get invoked.
- ✅ **Sidebar nav cleanup** (2026-08-25) — removed "This Week" from `Sidebar.tsx`; `/this-week` is a pure redirect to `/home` (kept only for old bookmarks), fully redundant with "Home" once `/home` became the current-week view.
- ✅ **Stray seed/fixture data cleanup** (2026-08-25) — found while investigating a real account never receiving its check-in reminder: a `CheckIn`/`WeeklyPlan`/`PlanItem` trio seeded into the account with a `respondedAt` dated *before* that week even started, which made the real reminder sweep think that week's slot was already handled. Confirmed synthetic (literal `seed...`-prefixed ids, zero matching `Notification` rows, a timestamp the real pipeline couldn't produce) and deleted just that trio, leaving older seed history untouched.
- ✅ **"Same as last week?" moved into a modal** (2026-08-25) — same reasoning as the draft-review modal above: this was a permanent stack of full-size item cards sitting above the priorities box even when there was nothing to review. Now a modal (auto-opens when there are unmatched previous-week items, same reopenable-banner pattern as the draft review). Checkbox replaced with a clickable card (the whole title/time block toggles selection; selected/unselected shown via opacity + tint rather than a checkbox glyph) plus a separate per-item dismiss (×) button for "don't copy this one, ever" — distinct from the checked/unchecked bulk-copy selection. The same hidden-checkbox-plus-`:has(:checked)` treatment was applied to the Settings/Onboarding "What matters most to you?" category chips for consistency — no visible checkbox anywhere in the app now, just clickable pills that show selected state through color.
- ✅ **Regenerate silently forgetting earlier adjustments** (2026-08-25) — real bug found via live testing: requesting fitness *and* chores across two different "Request changes" rounds meant they were never both scheduled, appearing to "trade off" against each other. Root cause: `POST /api/weekly-plan/[id]/regenerate` read `weeklyPlan.priorities` from the DB but never wrote an updated value back — each regenerate only ever saw *original priorities + the single latest adjustment*, so any earlier round's adjustment vanished from context the moment a second regenerate happened. Fixed by persisting the accumulated priorities text on every regenerate. Also added an explicit contradiction-handling instruction to `generateWeeklyDraft`'s system prompt after live-testing a deliberate stress case ("keep it light" + "pack the week" together) — Claude was already resolving toward the safer light interpretation, but silently; now it says so in the summary. Both verified live: the regenerate fix via a direct reproduction script (5/5 runs correctly included both FITNESS and CHORES from one combined request), the contradiction fix via 5 more runs all correctly surfacing the resolution in the summary text. New permanent eval scenario added to `scripts/eval-prompts.ts` for the contradiction case.

New `User.password` column (nullable — null for OAuth-only accounts; `authorize()` checks for that and fails cleanly rather than crashing on a null hash). Same email can't have both an OAuth and a credentials account (account linking isn't supported) — signup returns a generic "already exists" error either way, not distinguishing which case it is. Fully verified live end to end, including the actual browser login/signup flow, not just the server-side checks.
  - **The entry page (`src/app/page.tsx`) got a full redesign alongside this** — it was a bare, top-left, unstyled OAuth button before; now a centered hero card matching the rest of the app's design system, with a tagline. Credentials form is the primary path (form first), Google as a secondary option below it — styled to Google's own brand convention (white background, bordered, the real multi-color "G" mark, `GoogleIcon.tsx`) rather than the app's accent color, since a branded sign-in button isn't supposed to be re-themed. Microsoft/Apple OAuth buttons were removed entirely (see the declined entry above) — they were dead buttons pointing at providers Auth.js doesn't actually have registered.
  - **Three real CSS bugs found and fixed during this pass**, all through live screenshot iteration rather than caught by typechecking: (1) `input[type="email"]`/`input[type="password"]` were missing from the shared themed-input selector — they were rendering as fully unstyled native browser inputs ("grey blobs"); (2) no `::placeholder` color rule existed anywhere in the app, so placeholder text everywhere relied on browser defaults; (3) a genuinely subtle cascade bug — a plain-text "toggle" button's `:hover` rule only overrode `color`/`text-decoration`, not `background`, so the *base* `button:hover` rule's solid-fill background won for that one property on hover, and since the hover text color was set to the same color as that background, the text became invisible. Diagnosed by reading the browser's actual Styles panel (not guessed) after confirming server-rendered HTML and served CSS both matched source — a good example of ruling out the server side definitively before concluding the bug had to be in the cascade itself.
- ✅ **Scheduled hard-delete purge job** (2026-08-23) — `src/backend/jobs/purgeDeletedAccounts.ts`, daily sweep (`src/worker/scheduler.ts`), 30-day grace period after `deletedAt` is set. Every model's `userId` relation is `onDelete: Cascade` (verified directly in the schema before relying on it), so a single `deleteMany` on `User` cleanly cascades everything — no manual per-table cleanup needed.
- ✅ **User data export** (2026-08-24) — `GET /api/account/export`, a downloadable JSON file with every model tied to the user (`password` deliberately excluded even hashed — no legitimate reason for an export to include credential material). Built first, then reconsidered: a raw JSON file is the standard data-portability format, but not something a non-technical user would ever open or get anything out of — "why would I want to download a JSON" was the exact right question to ask. Added `/settings/export` (`DataSummaryPage`) as the *primary* path instead: every week laid out chronologically the same way the rest of the app shows one, with `@media print` styles (`globals.css`) so the browser's own "save as PDF" produces something actually worth keeping — no new PDF-generation dependency needed for that. JSON export is still there as a secondary "technical backup" link on that same page, not removed, since it's still the right format for genuine data portability, just not the primary offering. Added `a.secondary` to `globals.css` along the way — the existing `.secondary` look was scoped to `button.secondary` only, so an anchor styled to match needed its own rule.

## Other suggestions

- ✅ **Cost guardrails on Claude-calling routes** (2026-08-23) — initial draft creation was already capped to once/week by `WeeklyPlan`'s own `@@unique([userId, weekOf])`, but regenerate had no limit at all. New `WeeklyPlan.regenerateCount` field, capped at 5 per plan (`src/app/api/weekly-plan/[id]/regenerate/route.ts`), 429 with a clear message once hit. Also found and fixed a related gap while in this code: the check-in submit route had no idempotency guard — a check-in stays `PENDING` until the separate `/resolve` call, so a second `/submit` call (double-click, retry) before that would silently re-run everything, including a second real Claude call and a duplicate `Recommendation` row. Fixed with a `respondedAt` check.
- **A small automated test suite**, starting with `src/backend/week.ts`'s timezone math — not yet built.
- **Deploy something bare-bones early**, even before Phase 3 is polished. Production tends to surface a different class of problem (env vars, cron scheduling on Railway, email deliverability) than local dev does, and it's cheaper to find those before more is built on top.
